# 架构设计题答案

## 模块一：Context / Performance

### 1. 第一轮长窗口或多模态输入时，first token 很慢，怎么把 5-10 秒稳定压到 2 秒左右？

我会把方案分成四层，优先做收益最高、工程成本最低的：

1. `prompt prefix caching / context caching`
2. 输入预压缩
3. 路由与预热
4. 体感优化

#### 第一优先级：前缀缓存

如果长上下文里有大量稳定前缀，比如：

- system prompt
- 项目说明
- 历史摘要
- 用户 profile

那最有效的办法不是“优化提示词”，而是缓存它的 prefill / KV cache。

工程上可以做：

- 把稳定前缀切成 cacheable prefix
- 用户每次只增量追加最近消息
- 命中缓存后只对增量部分 prefill

优点：

- 降 TTFT 最直接
- 通常还能降费用
- 对用户行为几乎无感知

如果模型或供应商支持 prompt caching，这是优先级最高的低成本手段。

#### 第二优先级：输入预压缩

把“大而全输入”拆成“两阶段输入”：

1. 廉价模型或规则做结构化抽取 / 摘要 / OCR / caption
2. 主模型只看压缩结果 + 必要原文片段

例如：

- 文档很长：先抽提标题、章节、关键表格、关键数字
- 图像很多：先 OCR / 图片标签化，再送主模型
- 长聊天窗口：先用 rolling summary 替换老消息

优点：

- 减 prefill 长度
- 成本低
- 不一定需要改主模型

#### 第三优先级：路由与预热

很多请求根本不需要“大上下文大模型”。

可以做两层路由：

1. 轻量路由器判断是否需要大窗口
2. 不需要时直接走小模型 / 小上下文

另外可以做输入期预热：

- 用户输入过程中先做 session prefetch
- 用户点发送时已有部分准备好的上下文

这类办法对交互类产品很有效。

#### 第四优先级：体感优化

严格说它不一定减少真实 TTFT，但能明显提升主观体验：

- 先流式输出骨架句
- 先回一句状态反馈
- 先显示“已收到，正在查文档/执行工具”

用户体验上，从“空等 5 秒”变成“0.3 秒看到系统开始动”，差异很大。

#### 推荐组合

如果目标是把 5-10 秒稳定压到 2 秒左右，我会优先做：

1. prefix caching
2. 旧上下文 rolling summary
3. 多模态预提取
4. 小模型路由
5. 流式骨架反馈

这套方案通常是收益/复杂度比最好的。

### 2. 一个 session 连续聊了 200 轮，context 快爆了，怎么压缩？如何保证压缩后还流畅？

我会做“三层记忆”：

1. 近期原文窗口
2. 滚动摘要
3. 检索式长期记忆

#### 第一层：近期原文窗口

最近几轮必须保留 verbatim。

因为用户追问、指代、上下文依赖，最容易发生在最近对话里。

实践上一般保留：

- 最近 4-10 轮用户-助手交互
- 或最近 2k-8k token 原文

#### 第二层：滚动摘要

更早的历史不保留逐轮原文，而是压成一个持续更新的摘要块。

摘要里必须保留：

- 用户目标
- 关键决策
- 重要数字
- 时间/地点/人名
- 已调用过什么工具，结果是什么
- 还没完成的事项

而且压缩必须在完整轮次边界切分，不能把 assistant tool call 和 tool result 拆开。

#### 第三层：检索式长期记忆

不是所有信息都适合放在摘要里。

例如：

- 用户偏好
- 长期身份事实
- 常见工作背景

应该单独抽出来做 structured memory 或 semantic memory。

后续按 query-time 检索注入，而不是永远塞在 summary 里。

#### 如何保证压缩后仍流畅

关键点有四个：

1. 近几轮原文绝对不动
2. 摘要保留“对后续回答真正有用的信息”
3. 重要事实不只放摘要，还要结构化抽取
4. 压缩后做自检

自检可以很简单：

- 用小模型检查摘要是否覆盖“用户当前目标、待办、关键实体”
- 或在压缩 prompt 中强制要求保留这些字段

#### 推荐工程形态

- recent window：最近 6 轮原文
- running summary：老历史压缩成一段摘要
- memory store：用户画像 / 长期事实单独存
- query-time retrieval：本轮问题相关的长期记忆再注入

这是目前最稳妥的工业实践。

## 模块二：Memory

### 1. 半个月后用户问了以前问过的问题，Agent 如何更合理地做 memory 召回？

我不建议“启动时全量塞 memory”，而建议：

- query-time recall
- 混合检索
- 有来源标注地注入 system 区

#### 时机

用户发来当前问题后再召回，而不是预先把所有长期记忆灌进 prompt。

原因：

- 节省 token
- 降低噪音
- 减少过时记忆污染当前问题

#### 检索策略

理想上做 hybrid retrieval：

- 语义向量检索
- BM25 / 关键词检索
- 时间衰减
- 重要性权重

如果是“以前问过的问题”，还要区分两类：

1. 历史事实
2. 历史结论

例如“我在哪个城市工作”属于事实；
“你上次怎么比较向量数据库方案的”属于历史结论。

召回时最好带上：

- 来源时间
- 来源 session
- 置信度

#### 放置方式

我会把召回结果放到 system prompt 的“长期记忆”区域，而不是伪装成 user message。

示例语义：

- 长期记忆：用户的工作城市是上海（2026-09-01）
- 若与本轮对话冲突，以本轮为准

#### 冲突处理

如果长期记忆和当前输入冲突：

- 当前输入优先
- 回答时显式确认

例如：

- memory 说“用户在上海工作”
- 当前用户说“我已经搬到杭州了”

那应该基于杭州继续回答，并把 memory 更新掉。

### 2. 你理解的 Agent memory 经典框架是什么？发展趋势是什么？头部玩家怎么做？

#### 经典框架

经典上一般分四层：

1. `working memory`
2. `episodic memory`
3. `semantic memory`
4. `procedural memory`

working memory：

- 当前上下文窗口
- 最近轮次原文

episodic memory：

- 历史对话与事件记录
- 可以追溯“发生过什么”

semantic memory：

- 跨会话稳定事实
- 用户画像、偏好、背景

procedural memory：

- 如何做事
- 用户偏好的工作流
- 工具使用习惯

#### 代表性路线

- 向量库式 memory：最早最常见
- MemGPT / Letta：把上下文看成 RAM，把外部存储看成磁盘
- Generative Agents：强调 importance / recency / reflection
- Mem0 / Zep / Graphiti：往“记忆基础设施层”演化

#### 发展趋势

从“把历史切块做检索”走向“记忆是 runtime 的一等公民”。

趋势包括：

1. 读写分离
2. 结构化抽取与冲突消解
3. 时序化
4. agent 自主决定什么时候写、什么时候读
5. 用户可见、可删、可纠正

#### 头部玩家怎么做

OpenAI / ChatGPT：

- 明显走“可见可控的用户级记忆”路线
- 跨会话持久
- 用户可管理

Anthropic / Claude：

- 更强调项目级上下文与 agentic working memory
- 配合工具能力做强行动流

基础设施玩家（Mem0 / Zep / Graphiti / Letta）：

- 把 memory 做成独立能力层
- 提供检索、抽取、图谱、时序、冲突管理 API

我认为未来的主流不是“单一向量库”，而是：

- recent context
- structured facts
- episodic archive
- retrieval orchestration

协同工作。

## 模块三：Task

### 1. 长程任务里模型会忘记目标，有哪些解决方案？优缺点是什么？

常见方案有五类。

#### 方案一：目标卡 / plan file 外置

把目标、验收标准、进度写在外部状态里，每轮都注入。

优点：

- 简单
- 稳定
- 对模型遗忘最有效

缺点：

- 占 token
- 需要格式纪律

#### 方案二：定期摘要“已完成 / 剩余 / 下一步”

每 N 轮自动生成一次 task state summary。

优点：

- 比完整 plan 更短
- 易于注入

缺点：

- 摘要可能失真

#### 方案三：planner-executor 分层

上层负责规划，下层负责执行。

优点：

- 长任务更稳
- 可恢复
- 可并行子任务

缺点：

- 系统复杂度上升
- 子任务之间的上下文衔接要额外设计

#### 方案四：自校验 / verifier loop

定期让模型检查：

- 当前是否偏离目标
- 是否满足验收条件

优点：

- 能中途纠偏

缺点：

- 成本更高

#### 方案五：事件日志驱动的外部 runtime

不是把目标完全放在 LLM 脑子里，而是：

- 目标在外部状态机 / event log 中长期存在
- 模型只是对状态做下一步决策

优点：

- 最稳
- 最可恢复

缺点：

- 工程实现重

#### 我会怎么组合

工程上最稳的是：

1. 目标卡
2. task summary
3. verifier
4. 外部状态持久化

### 2. 用户要求“每天早上 9 点根据昨天聊天情况做复盘总结”，你会怎么设计？

我会按“调度层 + 数据层 + 生成层 + 通知层”来设计。

#### 调度层

- 定时任务系统触发
- 以用户本地时区为准
- 每天 9:00 生成一个 summary job

#### 数据层

- 从 session 存储里拉取“昨天 0:00-24:00”的会话数据
- 多个 session 按时间合并
- 数据量大时先分块再归并

#### 生成层

使用专用 prompt 生成结构化输出，例如：

- 昨天做了什么
- 关键决策
- 未完成事项
- 风险
- 今日建议

最好产出 JSON，然后再渲染成人类可读版本。

#### 通知层

- App push
- 邮件
- IM 卡片

用户点开后可以进入一个与这次复盘绑定的新 session，继续追问。

#### 工程要点

- 幂等：重复执行不重复推送
- 可溯源：每条总结最好能关联原消息 ID
- 失败重试：任务失败要告警
- 隐私：支持脱敏
- 成本：分块摘要用便宜模型，最终汇总用更强模型

## 模块四：Tool / Session Runtime

### 1. 异步工具不能让用户一直等，但结果很重要，怎么设计？

我会把异步工具建模成 `submit / poll / notify` 三段式。

#### 提交阶段

Agent 调用异步工具时，runtime 立即返回：

- `job_id`
- `status=queued/running`
- 预计完成时间

然后 LLM 可以对用户说：

- 我已经开始跑这个任务
- 结果出来会通知你

#### 执行阶段

异步 worker 在后台执行，结果持久化。

#### 回传阶段

两种方式：

1. pull：用户下次发消息时顺带检查异步结果
2. push：结果完成时直接投递事件进 session

如果结果很重要，我会做 push + pull 双保险。

#### 关键点

- job id 幂等
- 结果持久化
- 超时 / 重试 / 死信队列
- session 级事件队列串行消费

### 2. 如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？

我不会让多个线程直接同时写一个 session，而会设计成：

- 每个 session 一个串行事件队列
- 一个 actor / mailbox

所有输入都变成事件：

- user_message
- tool_result
- async_job_done
- cancel
- timeout

然后串行消费。

#### 当 busy 时用户又发消息

常见策略有三种：

1. 排队
2. 打断
3. 合并

默认我建议排队：

- 先提示“当前正在执行上一轮”
- 新消息进入队列
- 当前轮结束后再处理

如果产品需要“打断”，则必须额外处理：

- 已产生的工具副作用如何回滚
- 未完成工具任务如何取消

#### 当异步工具完成事件到达

也进入同一个 session 队列。

如果当前 busy：

- 不直接打断当前推理
- 等当前轮结束后再处理这个事件

这样最稳，状态也最容易推理。

## 模块五：Agent Runtime 架构对比

### 1. Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？优缺点是什么？

核心差异是“工具调用在协议里被建模成什么”。

#### OpenAI-compatible 风格

通常是：

- assistant message 上带 `tool_calls` 字段
- tool result 用 `role=tool`

优点：

- 结构化
- 易解析
- 兼容生态最广
- 大量厂商都支持

缺点：

- 协议相对僵硬
- 思考、文本、工具块的交错表达能力一般

#### Claude / Anthropic 风格

更强调 content block 化：

- 思考块
- tool use block
- tool result block

它天然更适合做“边想边调工具边继续想”的交织式 agent 行为。

优点：

- 流式体验更自然
- 多模态工具结果承载更顺
- 行为表达力更强

缺点：

- 兼容 OpenAI 生态时要做额外适配
- 对工程实现者来说，内容块解析更复杂

#### Claude Code 的特别之处

Claude Code 这类 coding agent 通常把工具输出当“高保真原始材料”，例如：

- 文件读取原文
- shell stdout/stderr
- patch diff

优点：

- 模型修 bug 时信息更完整

缺点：

- 输出可能极长
- 更依赖外部 runtime 做截断与裁剪

### 2. OpenHands 的状态机设计有什么优缺点？更优雅的实现方式是什么？

#### OpenHands 式状态机的优点

- 控制流明确
- 可暂停 / 可恢复
- 易插入人工确认点
- 对预算和安全策略友好

#### 缺点

- 状态容易膨胀
- 增加异步事件、并行工具、外部回调后转移复杂
- 很多逻辑会散落在状态转移分支里

#### 我更偏好的做法

“事件溯源 + session actor”。

也就是：

- 一切输入都记为事件
- session 状态由事件流 fold 得出
- 每个 session 一个串行 actor 处理 mailbox

优点：

- 天然适配 busy / async completion / interrupt
- 可重放调试
- 更适合长期演进

状态机依然可以保留，但更适合做“高层状态标签”，而不是把全部 runtime 逻辑都硬编码在状态转移里。
